# OpenRouter request inventory (brief C1)

Every OpenRouter call the app makes, with the body fields it sends and when. Line references are to the
code at the time of C1 (commit on branch `worktree-agent-adb5d14e474db71c2`). The bodies were checked
against the live app code by `npm run contract:check`, which captures them through the app's own
builders. Routing matters only where a body sets `provider.require_parameters`, because then OpenRouter
sends the call only to an endpoint that accepts every parameter in the body.

Base URL `https://openrouter.ai/api/v1`. Every call sends `Authorization`, `HTTP-Referer` and `X-Title`
(`src/services/openrouter/transport.ts`, `buildHeaders`). Retries: up to 3, for retryable errors only.

Notes:

- `usage: {include: true}` is on every chat call. OpenRouter does not list it in `supported_parameters`, and analysis has worked on device with it, so the check treats it as envelope (`ENVELOPE_FIELDS` in `rules.mjs`).
- Calls 1-4, 6 and 7 rely on `canUseStructuredOutput` (`chat.ts`): structured output is used only when the model lists `structured_outputs` in the catalogue. Otherwise the JSON-only instruction is used and no `require_parameters` is sent.

## Generation lookups

None. The app never calls `GET /generation`. It reads the generation id from the `x-generation-id` response header (or the body `id`) and stores it in the usage ledger (`chat.ts` `sendChatCompletion`, `speech.ts`).

## What `contract:check` judges, and what it cannot

| Rule                                                                                                                                                            | Source                                                   | Checked by                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------ |
| Every chat call with `require_parameters` has an endpoint that accepts structured output and every parameter in its body                                        | live `/models/<id>/endpoints` `supported_parameters`     | calls 1, 2, 6, 7 (`structuredCallVerdict`) |
| Default text models are listed, and their prices are present and parseable                                                                                      | live `/models?output_modalities=text`                    | `catalog (text)`, `pricing`                |
| Each narrator and each of the five newest narratable speech models is listed, served, and gets a voice from its `supported_voices` (or none when it takes none) | live `/models?output_modalities=speech` and `/endpoints` | speech rows (`speechCallVerdict`)          |
| `instructions` is sent only where the style rule says so                                                                                                        | `supportsStyleInstructions` (app code)                   | speech rows                                |
| `speed` is within the documented 0.25 to 4 range                                                                                                                | OpenRouter docs                                          | speech rows                                |
| Prices for every curated speech model are parseable                                                                                                             | live `/models?output_modalities=speech`                  | `pricing` rows                             |

Cannot be checked from public data, and so reported as limits, not FAILs:

- Speech `response_format`: speech endpoints publish no supported parameters. The app relies on `speechFormatFor` (PCM for Gemini TTS) and on the one-time format retry.
- Speech `speed` acceptance per provider: not published. The app sends `speed: 1` on every call. The device has narrated with it, so it is accepted by the models in use.
- Calls 5, 8 and 9 have no `require_parameters`, so there is no routing constraint to check.
- The vocab call reads its two constants from `src/features/vocab/vocab-actions.ts` with a source read, because they are not exported. A missing constant stops the check with exit 3.
